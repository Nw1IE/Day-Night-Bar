# Подключение домена и HTTPS к работающему BarSite

Эта инструкция предназначена для **уже работающего** сайта на VDS с Ubuntu 22.04. Она не предполагает переустановку проекта и не требует менять работающие порты, пересобирать контейнеры или переносить данные.

- IP сервера: `132.243.190.79`.
- Основной домен: `day-night-bar.ru`.
- Дополнительный адрес: `www.day-night-bar.ru`.
- Команды ниже выполняются на VDS по SSH, если не указано иное.

## Как это устроено

В панели DNS домену назначают IP сервера. Это **не отключает работу сайта по IP**: браузер, обращаясь к домену, узнаёт тот же IP и подключается к тому же серверу. Затем Nginx по имени домена выбирает конфигурацию сайта. Certbot получает сертификат для домена и помогает настроить HTTPS. Отдельной кнопки «переключить VDS с IP на домен» нет.

Для основного домена в SEO проекта уже указан адрес `https://day-night-bar.ru/`. Сертификат для домена не делает HTTPS по самому IP автоматически рабочим; проверять защищённое подключение следует по имени домена.

## Шаг 1. Проверьте домен в панели регистратора

1. Войдите на сайт регистратора, где куплен домен. Откройте «Мои домены» → `day-night-bar.ru` → «DNS-серверы» или «Управление DNS» (названия зависят от регистратора).
2. Убедитесь, что домен делегирован и активен. Редактировать записи нужно **у провайдера, чьи NS-серверы действительно указаны для домена**. Если NS ведут к другому DNS-провайдеру, изменения в неиспользуемой зоне регистратора результата не дадут.
3. В активной DNS-зоне должны быть записи:

| Тип | Имя / хост | Значение |
| --- | --- | --- |
| A | `@` — корень домена | `132.243.190.79` |
| A | `www` | `132.243.190.79` |

В некоторых панелях вместо `@` нужно оставить имя пустым. Если обе записи уже правильные, повторно их создавать не нужно. Если для `www` уже есть корректный CNAME на основной домен, отдельная A-запись не требуется. Существующие настройки почты и других поддоменов не меняйте.

Подключитесь по SSH и проверьте ответы публичных DNS:

```bash
sudo apt update
sudo apt install -y dnsutils curl
dig +short NS day-night-bar.ru
dig @1.1.1.1 +short A day-night-bar.ru
dig @1.1.1.1 +short A www.day-night-bar.ru
dig @8.8.8.8 +short A day-night-bar.ru
dig @8.8.8.8 +short A www.day-night-bar.ru
dig @1.1.1.1 +short AAAA day-night-bar.ru
dig @1.1.1.1 +short AAAA www.day-night-bar.ru
```

В ответах для A обоих имён должен быть `132.243.190.79`. Для CNAME в ответе также может отображаться имя, на которое он ссылается. Если присутствуют другие A-адреса, выясните, зачем они нужны: посетители и проверка сертификата могут попасть на другой сервер. Если есть AAAA, IPv6 должен вести на этот же сайт и обслуживаться на портах 80 и 443; иначе исправьте эту запись у DNS-провайдера. Если IPv6 намеренно не используется, некорректную AAAA-запись можно удалить. Дождитесь распространения DNS; значения в разных сетях могут обновиться не одновременно.

## Шаг 2. Проверьте сайт по домену до HTTPS

С VDS выполните:

```bash
curl -i http://day-night-bar.ru/
curl -i http://www.day-night-bar.ru/
curl -i http://day-night-bar.ru/api/menu
curl -I http://day-night-bar.ru/imgs/1.jpg
```

Проверьте также `http://day-night-bar.ru/` в браузере на телефоне через мобильную сеть. Главная должна показывать ваш бар, `/api/menu` — JSON, картинка должна отвечать успешно. Для обычного меню допустим и пустой JSON-массив. Если по домену уже открывается правильный сайт и запросы работают, DNS и HTTP-маршрутизация в целом настроены; переходите к шагу 4. Сайт при этом может по-прежнему открываться и по IP — это ожидаемо.

Если открывается чужая или стандартная страница Nginx, либо домен не открывается, продолжайте со шага 3. Запросы с самого VDS не заменяют проверку извне: firewall и DNS в разных сетях могут отличаться. Подстановка `Host` ниже помогает проверить выбор виртуального хоста отдельно от DNS:

```bash
curl -i -H 'Host: day-night-bar.ru' http://127.0.0.1/
```

## Шаг 3. Если сайт по домену не открывается: найдите и поправьте существующий Nginx

Сначала определите, кто принимает HTTP. На сервере выполните:

```bash
sudo ss -lntp | grep -E ':(80|443)\b'
sudo systemctl is-active nginx
docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

**Если системный Nginx активен и именно он принимает публичные запросы на 80**, найдите его работающую конфигурацию:

```bash
sudo nginx -t
sudo nginx -T 2>&1 | grep -n -E 'configuration file|server_name|listen |proxy_pass|location /'
```

В выводе `# configuration file /путь/к/файлу:` указывает начало файла. Найдите тот `server { ... }`, который сейчас обслуживает ваш сайт на порту 80, его `location /`, `/api/` и `/imgs/`. При необходимости посмотрите конкретный файл через `sudo less /полный/путь/к/файлу`. Не публикуйте полный вывод `nginx -T`: он может содержать чувствительные настройки.

Сохраните копию **найденного** файла, подставив его реальный путь вместо примера:

```bash
sudo cp -a /полный/путь/к/файлу /полный/путь/к/файлу.before-domain
sudo nano /полный/путь/к/файлу
```

В существующем HTTP-блоке сайта найдите строку вида:

```nginx
server_name _;
```

Добавьте имена домена в эту же директиву. Например, если текущая строка выглядит как выше:

```nginx
server_name day-night-bar.ru www.day-night-bar.ru _;
```

Если в строке уже есть другие имена, сохраните их и допишите два новых имени до `;`. Если директивы `server_name` в блоке нет, добавьте строку с двумя доменами внутрь соответствующего `server { ... }`. **Не создавайте второй `server_name` в том же блоке** и не меняйте `listen`, `location`, `proxy_pass`, порты, пути, другие сайты и существующие заголовки. Пример строки выше — не готовая конфигурация всего сервера.

В nano сохраните `Ctrl+O`, Enter, затем выйдите `Ctrl+X`. Применяйте только если проверка успешна:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Если `nginx -t` сообщает об ошибке или конфликте имён, не выполняйте reload: исправьте конфигурацию либо восстановите копию по реальному пути и снова проверьте `sudo nginx -t`. Если reload уже был выполнен и сайт работает неправильно, восстановите исходный файл и выполните проверку и reload. Повторите шаг 2.

**Если на 80 напрямую отвечает Docker-контейнер, системный Nginx не используется или установлен Nginx Proxy Manager/другой прокси**, эта инструкция с `certbot --nginx` на хосте неприменима без адаптации: плагин не установит сертификат внутрь контейнера автоматически. Не меняйте compose и порты наугад. Сохраните вывод трёх диагностических команд из начала шага и определите используемый прокси; потребуется схема именно для него. Важно также не направлять Nginx обратно на тот же адрес и порт, который он сам слушает.

## Шаг 4. Откройте доступ для проверки сертификата

Для выпуска и будущего продления через HTTP-01 должны быть доступны **внешний TCP 80**, а для посетителей HTTPS — TCP 443. Проверьте правила у хостинг-провайдера и на сервере:

```bash
sudo ufw status verbose
```

Если UFW активен и порты закрыты, разрешите их, не меняя доступ к SSH:

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

Если UFW не активен, не включайте его без отдельной проверки действующего SSH-порта и правил: это может отрезать доступ к VDS. Если используется другой firewall, настройте правила в нём. Проверьте оба HTTP-адреса из внешней сети по шагу 2.

## Шаг 5. Установите Certbot и получите сертификат

Этот шаг подходит для **системного Nginx**, который работает с текущей конфигурацией и обслуживает оба домена по HTTP. Перед запуском сохраните копию изменяемого файла из шага 3: Certbot может изменить конфигурацию Nginx. Если сайт уже открывался по домену, всё равно найдите и сохраните его конфигурацию перед продолжением.

```bash
sudo apt update
sudo apt install -y certbot python3-certbot-nginx
sudo nginx -t
sudo certbot --nginx -d day-night-bar.ru -d www.day-night-bar.ru
```

При запросе введите действующий email, примите условия, если согласны, и следуйте подсказкам. Если Certbot спрашивает о перенаправлении HTTP на HTTPS, выберите перенаправление. Если `www` не настроен и не нужен, исключите `-d www.day-night-bar.ru`: включённое в сертификат имя тоже обязано пройти проверку.

Если Certbot сообщает об ошибке, не повторяйте команду много раз подряд: сначала проверьте DNS, публичный порт 80, IPv6 и `server_name`. Certbot настраивает TLS; маршруты API и изображений должны уже работать до его запуска.

## Шаг 6. Проверьте HTTPS и приложение

```bash
sudo nginx -t
sudo certbot certificates
curl -I http://day-night-bar.ru/
curl -I https://day-night-bar.ru/
curl -I http://www.day-night-bar.ru/
curl -I https://www.day-night-bar.ru/
curl -i https://day-night-bar.ru/api/menu
curl -i https://day-night-bar.ru/api/promotions
curl -I https://day-night-bar.ru/imgs/1.jpg
```

Ожидается: HTTP перенаправляет на HTTPS, основной адрес возвращает страницу без ошибки сертификата, API возвращает JSON, картинка — успешный ответ с типом изображения. Откройте `https://day-night-bar.ru/` на компьютере и телефоне, проверьте меню, категории, акции, картинки, переключение темы и вход в админку. Проверьте адрес `https://www.day-night-bar.ru/`: оба имени должны быть в сертификате, если используются.

Для SEO основной адрес уже задан без `www`. Постоянный редирект с HTTPS `www` на основной домен полезен, но Certbot не гарантирует его автоматическую настройку. Его следует добавить после просмотра реальных SSL-блоков Nginx, сохранив сертификат для обоих имён и путь запроса; не добавляйте вслепую второй блок с теми же `listen` и `server_name`.

Если страница открылась, но запросы или картинки уходят на старый IP или `http://`, посмотрите адреса запросов во вкладке Network браузера. В проекте клиент использует `VITE_API_URL` и `VITE_IMAGES_URL`, а значения Vite встраиваются при сборке. Относительные `/api` и `/imgs` позволяют использовать текущий домен, но **не меняйте `.env` и не пересобирайте клиент вслепую**: работающая версия на VDS может отличаться от репозитория. Сначала сравните код и настройки, сохраните рабочую версию и проверьте после изменения. Несколько адресов через `;` в одном `VITE_API_URL` не являются списком альтернатив.

## Шаг 7. Проверьте автоматическое продление

Пакет Certbot обычно уже устанавливает планировщик. Сначала проверьте наличие таймера или cron:

```bash
systemctl list-timers --all | grep -i certbot
systemctl status certbot.timer --no-pager
sudo grep -R certbot /etc/crontab /etc/cron.d /etc/cron.daily 2>/dev/null
```

Если `certbot.timer` существует, но выключен, включите его:

```bash
sudo systemctl enable --now certbot.timer
systemctl list-timers --all | grep -i certbot
```

Если таймера нет, но есть штатное cron-задание с `certbot renew`, дополнительный таймер не нужен. Если нет ни того ни другого, сначала проверьте способ установки Certbot и установите штатный механизм для него, не создавая дублирующих заданий.

Проверьте пробное продление:

```bash
sudo certbot renew --dry-run
```

Должно завершиться успешно. Для диагностики используйте:

```bash
sudo journalctl -u certbot.service --since '30 days ago' --no-pager
sudo tail -n 100 /var/log/letsencrypt/letsencrypt.log
```

Проверяйте срок сертификата командой `sudo certbot certificates`, следите за почтой Certbot и настройте внешний мониторинг HTTPS с уведомлением об истечении. Автопродление снижает ручную работу, но не гарантирует бессрочную доступность: должны работать домен и DNS, сервер и его часы, публичный порт 80, планировщик, Certbot и Nginx.

## Шаг 8. Завершите SEO после развёртывания изменений

Если подготовленные SEO-изменения уже перенесены на VDS, откройте:

```bash
curl -i https://day-night-bar.ru/robots.txt
curl -i https://day-night-bar.ru/sitemap.xml
```

Проверьте HTTP 200 и содержимое файлов. Добавьте сайт в Яндекс Вебмастер и Google Search Console, подтвердите права и отправьте `https://day-night-bar.ru/sitemap.xml`. Если SEO-код ещё не развёрнут, перед обновлением сравните серверную рабочую версию и репозиторий: локальные незапушенные исправления на VDS нельзя терять.
